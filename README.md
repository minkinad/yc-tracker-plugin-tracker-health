# Tracker Health

[![CI](https://github.com/minkinad/yc-tracker-plugin-tracker-health/actions/workflows/ci.yml/badge.svg)](https://github.com/minkinad/yc-tracker-plugin-tracker-health/actions/workflows/ci.yml)

Контроль качества задач Yandex Tracker.

Tracker Health проверяет текущую задачу в Yandex Tracker и показывает, насколько она готова к работе.

Версия 0.1 работает полностью внутри плагина: она не использует ИИ, не отправляет данные задачи на внешний сервер и не требует отдельной базы данных.

## Проблема

Задачи часто уходят в работу без исполнителя, оценки, нормального описания или критериев приёмки. Недостающая информация обнаруживается уже после начала работы.

## Возможности

- Анализ текущей задачи в слотах `issue.block` и `drawer.issue.block`.
- Расчёт взвешенного Health Score от 0 до 100.
- Отображение пройденных и проваленных проверок.
- Краткое объяснение каждой проблемы.
- Конкретные рекомендации по исправлению проваленных проверок.
- Безопасная обработка загрузки и ошибок без падения интерфейса Yandex Tracker.
- Компактный интерфейс для карточки задачи.

## Как это работает

1. Tracker Plugin SDK передаёт текущую задачу через контекст слота.
2. Infrastructure Adapter проверяет данные Tracker и преобразует их в `IssueHealthContext`.
3. Domain Health Engine выполняет правила и рассчитывает результат.
4. Интерфейс на React показывает оценку, уровень здоровья, найденные проблемы и рекомендации.

```text
Tracker SDK
    ↓
Infrastructure Adapter
    ↓
Domain Health Engine
    ↓
UI
```

Доменный слой не импортирует React, Tracker SDK, браузерные и сетевые API или хранилище.

## Health Score

В расчёте участвуют только применимые правила. Правила со статусом `skipped` исключаются из `totalWeight`.

```text
score = round(passedWeight / totalWeight × 100)
```

Если применимых правил нет, движок возвращает итоговую оценку `0` без `NaN` или `Infinity`.

| Оценка | Уровень    | Статус в интерфейсе |
| ------ | ---------- | ------------------- |
| 90–100 | `healthy`  | Задача готова       |
| 70–89  | `warning`  | Есть рекомендации   |
| 0–69   | `critical` | Требует внимания    |

Статус всегда сопровождается текстом и иконкой, поэтому интерфейс не полагается только на цвет.

## Правила по умолчанию

В версии 0.1 используются шесть правил с суммарным весом 100.

| Rule ID               | Условие                                                             | Вес |
| --------------------- | ------------------------------------------------------------------- | --: |
| `assignee`            | Исполнитель существует.                                             |  15 |
| `priority`            | Приоритет существует.                                               |  10 |
| `description`         | Описание после `trim()` содержит не менее 100 символов.             |  20 |
| `issue-type`          | Тип задачи существует.                                              |  10 |
| `estimate`            | Оценка существует и больше нуля.                                    |  15 |
| `acceptance-criteria` | В описании присутствует поддерживаемый заголовок критериев приёмки. |  30 |

Правило `acceptance-criteria` регистронезависимо распознаёт Markdown-заголовки и обычные заголовки с двоеточием:

```text
## Acceptance Criteria
### Критерии приёмки
Критерии приемки:
Критерии готовности:
```

Случайное упоминание этих слов внутри предложения не считается секцией. Версия 0.1 проверяет только наличие заголовка и не анализирует смысл или качество содержимого секции.

## Архитектура

Tracker Health отделяет интеграцию с Tracker от бизнес-правил и представления:

- `src/app` — координация приложения и обработка ошибок.
- `src/infrastructure/tracker` — проверка и преобразование данных Tracker во время выполнения.
- `src/domain/health` — доменные контракты, правила и чистый Health Engine.
- `src/components` — компоненты представления на Gravity UI.
- `src/shared` — общие технические утилиты.
- `tests` — тесты доменного, инфраструктурного, прикладного и UI-слоёв.

Направление зависимостей:

```text
Yandex Tracker → infrastructure → domain → UI
```

Доменный слой не зависит от типов Tracker. Благодаря этому `evaluateIssueHealth()` остаётся детерминированной чистой функцией и может использоваться вне интерфейса плагина.

Полные контракты и ограничения v0.1 описаны в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Разработка

Требования:

- Node.js `>=22.12.0`;
- npm с поддержкой файла блокировки зависимостей;
- CLI для отладки плагина внутри слота Yandex Tracker.

Установите точные версии зависимостей из файла блокировки:

```bash
npm ci
```

Запустите локальный сервер Vite:

```bash
npm run dev
```

Если CLI плагина доступен, проверьте проект и откройте локальный плагин в Tracker:

```bash
weavix doctor
weavix debug
```

Плагин получает полный контекст задачи от хост-приложения. Обычный локальный запуск вне Tracker не предоставляет реальный контекст `issue.block`.

## Тестирование

Полный набор локальных проверок:

```bash
npm run lint
npm run typecheck
npm run test
npm run build
```

Режим наблюдения для разработки доменных правил:

```bash
npm run test:watch
```

Основной приоритет тестов — доменный слой: расчёт оценки, пропущенные правила, границы уровней, неизменяемость входных данных, граничные случаи правил, определение секции критериев приёмки и преобразование задачи Tracker. UI-тесты покрывают состояния загрузки, ошибки и все три уровня здоровья.

GitHub Actions выполняет `npm ci`, линтинг, проверку типов, тесты и производственную сборку для Pull Request и отправки изменений в `main`.

## Участие в разработке

1. Создайте ответвление (fork) репозитория и отдельную ветку для изменения.
2. Установите зависимости через `npm ci`.
3. Не добавляйте зависимости доменного слоя от React или типов Tracker SDK.
4. Добавляйте поведенческие тесты для изменений правил, расчёта оценки или преобразования данных.
5. Перед Pull Request выполните линтинг, проверку типов, тесты и сборку.

Сохраняйте Pull Request в границах текущего этапа. В рамках поддержки v0.1 не добавляйте ИИ, серверную часть, постоянное хранилище, аналитику всей очереди или возможности будущих версий.
